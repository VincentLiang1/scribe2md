# 開發護欄:讓 AI 協作的成果不會腐爛

**核心主張**:AI 的價值不只是打字快,是讓一批「一直以來划不來的事」變得划得來
——寫下每個決定的理由、把每個坑變成規則、為看不見的失敗寫稽核工具。
這個 Skill 裝的就是那批事的**做法**。

## ⚠️ 第一條規則:不要照抄別的專案的規則

來源專案的 `CLAUDE.md` 有九成**不該**被移植。它的價值來自「那個專案踩過的坑」
(某個 Windows 內建 DLL 會被優先載入導致崩潰、某個編碼會讓 cmd 跳到句子中間
執行文字)——這些對新專案是純雜訊,而且每次對話都吃掉上下文預算。

**要移植的是「怎麼長出規則」,不是規則本身。**

照抄的下場是一份看起來很專業、但沒有一條是為這個專案而寫的教條,
然後沒有人(包括 AI)真的遵守它。

## 分階段導入(不要第一天全套裝上)

來源專案這套是 **30 天長出來的**,照真實順序導入:

| 時機 | 裝什麼 | 為什麼是這個順序 |
| --- | --- | --- |
| **第 1 天** | `CLAUDE.md` 骨架(100 行內)+ 測試框架 + **紀律一** | 規則要有地方放,測試要有地方長 |
| **第 1 週** | 決策日誌格式、`test_docs_index.py` | 開始有文件了才需要守文件 |
| **有一批測試之後** | `mutate.py` 故障注入 | 沒有測試就沒有東西可以驗收 |
| **功能穩定後** | 規格書 `docs/spec/` | 需求還在變時寫規格 = 維護一份必然過時的文件 |

⚠️ 來源專案的規格書是**第 30 天**才補的,`mutate.py` 是第 27 天。
一開始就要求「先寫規格再開發」在探索性專案會嚴重拖慢——除非需求本來就明確
(那種情況適合 spec-driven,另案評估)。

## 紀律一:踩到坑,當場寫成規則(最重要,第 1 天就要有)

**做法**:每次踩到「讀程式碼看不出來、只有踩過才知道」的東西,當場說一句
「把這個教訓寫進 CLAUDE.md」。一次 30 秒。

**判準**——值得寫下來的是這幾種:

- 上游 API / 作業系統的反直覺行為(而且錯誤訊息完全不指向真因)
- 用推理會得到相反結論的事(實測數據要一起寫)
- 「壞掉的時候看起來很正常」的失敗模式
- 使用者拍板的決定(尤其是「不要做 X」)

**不值得寫的**:程式碼結構、git 歷史查得到的東西、只在這次對話有意義的東西。

### 規則升級階梯(⭐ 這是全篇最有用的一段)

規則**失守一次,就升一級**。來源專案的實例:一條「改文案要同步說明文件」
的規則,寫了兩遍、仍然在同一批改動裡漏掉第五個標籤:

| 級別 | 形式 | 可靠度 |
| --- | --- | --- |
| 1 | 寫進 `CLAUDE.md`(靠讀到、記得) | 機率性 |
| 2 | 改寫成**機械步驟**(「拿舊字串 grep 全 repo,改完再搜一次」) | 較高——不依賴記憶,依賴照做 |
| 3 | 變成**測試**(對不上就自動失敗) | 確定性,但只擋得住能斷言的東西 |
| 4 | 變成 **hook**(事件觸發、確定性執行) | 最強;⚠️ 來源專案尚未驗證,見文末 |

> **失守的從來不是規則,是「靠記得」這個做法。**
> 所以每次失守,問的不是「怎麼更小心」,是「這條能不能升一級」。

## 紀律二:文件一致性交給測試,不要交給記憶

「記得更新文件」是人力,「到底更新了沒有」可以自動查。**把這兩件事分開。**

用 `assets/test_docs_index.py`(幾乎原封可用,改兩個路徑常數):

- 正向:`CLAUDE.md` 指到的每一份文件都要真的存在
- 反向:`docs/dev/` 裡的每一份都要有人指得到 —— **沒有入口的文件等於不存在**

值得比照辦理的其他一致性(依專案而定):

- README 的功能清單 vs 使用說明的篇名
- CLI 的每一個參數 vs 說明文件(這個能精確比對,適合進測試)
- 使用者可見文案的格式慣例(來源專案掃的是 Markdown 粗體貼在全形引號外側,
  那在 CommonMark 下不構成粗體,會把星號原樣印出來)

⚠️ **不要什麼都自動判定**。來源專案的「說明涵蓋率」盤點刻意**不判定**,
只把清單擺出來讓人逐項看——因為說明常常用別的說法講同一件事,
**給假判定比不給更糟**。判準:能精確比對的進測試,需要人判斷的做成盤點腳本。

## 紀律三:測試本身要被驗收(⭐ AI 協作的關鍵一步)

**問題**:AI 很會寫測試,但它**看得到實作**,所以特別容易寫出
「描述程式碼剛好做了什麼」的測試——**那種測試永遠是綠的,包括程式壞掉的時候**。

這不是猜測。來源專案的實例:

- 一個「這份文件有沒有做過轉換」的欄位被寫死成永遠回報「沒有」
  (等於每份產物都在說謊)→ **974 條測試全綠**。
  原因:測試用假引擎把整支函式換掉,**真正做計算的那行從沒被執行**。
  一句話記住:**假引擎測得到接線,測不到計算。**
- 兩個關閉遙測的設定(專案的隱私硬性規格)→ **整套測試沒有一條在驗**,
  而它失效的樣子是「什麼都看不出來」。

**做法**:用 `assets/mutate.py`。把程式故意改壞 → 只跑對應測試 →
確認**真的變紅** → 在 `finally` 裡還原。

```
python scripts/mutate.py           # 全部跑一輪
python scripts/mutate.py M4 M18    # 只跑幾條
python scripts/mutate.py --list    # 列清單,不動檔案
python scripts/mutate.py --who M32 # 逃掉時:跑全套並印出誰真的紅了
```

**每條突變的 `why` 寫「這樣改壞之後,使用者會遇到什麼事」**,不是「改了哪一行」
——看報告的人要判斷的是「這個風險有沒有人守著」。

**逃掉的有三種,報告分不出來**:

1. **真的沒人守** → 補測試
2. **常數被符號引用**(測試拿同一個常數去算輸入再斷言,門檻怎麼改都跟著動)
   → 補**關係式斷言**(上下界 + 實測理由),不是把數字抄第二遍
3. **突變本身是 no-op** → 改突變,不是改測試

`--who` 分得出 1 和「只是綁錯測試」;分不出 3,那只能回頭讀突變後的程式碼。

⚠️ **還有第三種狀態 BROKEN(這條突變自己跑不起來),不可以跟 GREEN 混在一起**
——混了就會叫人去補一條其實已經存在的測試。兩種假訊號方向相反:pytest 的
exit 2~5 是它自己出問題(node id 打錯、測試改名、沒收集到測試),算成 RED 是
**假紅**;突變的 `old` 隨程式改動漂掉,算成 GREEN 是**假洞**。工具在
`main()` 開頭先跑 `_validate()`(撞號、字串漂掉、綁到改名過的測試、no-op)
當場擋下來——每一種的症狀都是「報告照印,只是失去意義」。

**什麼時候跑**:補完一批測試之後、或改動了帶回歸防線的邏輯之後。不必每次提交都跑。
**新增功能時把突變一起加進去**——一條測試沒被突變戳過,就只是「有跑過」而已。

⚠️ **沒被戳過的模組等於還沒驗收過**。來源專案某一輪 25/25 全紅,
一算才發現 45 個測試模組只戳過 9 個——**70% 的測試住在沒被戳過的模組裡**。

## 紀律四:不要用推理代替實測

AI 最貴的失敗模式不是「不會」,是**講得很有道理,但它沒有去看**。

**做法**:在專案裡放一份 `docs/dev/verification.md`,開頭第一句就是這條,
然後把「這個專案的東西該怎麼驗」逐項寫下來。實戰歸納的三條:

- **前端/樣式問題去看真實 DOM**,不要盲改 CSS。來源專案盲改三次都沒中,
  裝瀏覽器自動化看一次 `getComputedStyle`,兩分鐘結案(真相是那條「線」
  根本不是框線,是 1px 間隙露出底色)。判準:只要問題是「這個顏色/間距
  從哪來」,靜態閱讀一定落空。
- **對「看不出對錯」的產出要有客觀判準**。例:圖片文字辨識的錯字沒有聲音,
  改用「名片掃描檔的檔名就是正確答案」當判準,對錯不需要人來判斷。
- **矛盾的證據往往指向真因**。例:提高優先權沒用、減少執行緒更差
  ——兩個針對排程的手段同時無效,才推論出根因在底層鎖。

**規模才是觸發條件**:短樣本測不出崩潰,驗證要用真實規模的資料。

## `CLAUDE.md` 怎麼寫(用 `assets/CLAUDE.md.tmpl` 起手)

**它是唯一每次對話都自動載入的檔案**,所以:

- **只放「必須當場生效」的東西**。深度知識放 `docs/dev/*.md`,
  在 `CLAUDE.md` 留**觸發語**:「動到 X 之前先讀 `docs/dev/y.md`」
- **有預算意識**。來源專案曾經到 75,689 字元,後來壓到約 14,000
  (細節搬出去、留摘要與指路)。太長的下場是**指示被忽略的機率上升**
- **每條規則附上「為什麼」**。少了理由,下一次重構就會被順手改掉
- ⚠️ 搬出去之後**一定要有測試釘住指路**(紀律二),否則檔案改名/刪除時
  知識會**安靜地消失**——沒有人會知道那裡本來有東西

## 決策日誌:commit 訊息的格式

標題一句話講**結果**,內文寫:

1. **使用者要求什麼 / 為什麼這樣選**(含被否決的選項)
2. **代價的數字**(「整欄 +24px、按鈕下移 24px,1240×900 實測 736→760」)
3. **⚠️ 過程中踩到什麼**(這部分常常比程式碼本身值錢)
4. **稽核結果**(「六個舊字串全數零殘留,僅存三處是刻意保留的註解」)

外加一種特別的紀錄:**「已結案,不要再重開」**。
AI 很擅長提出優化建議,而每次重新評估都要花人的時間回答已經答過的問題
——更糟的是它可能真的動手改掉。**寫下結論的成本是三行字,重跑實測是半天。**

## 通用地雷(從實戰帶出來,不分語言)

- **改寫原始碼的工具一定要 `read_bytes`/`write_bytes`**。`read_text`/`write_text`
  一來一回會把 LF 換成 CRLF(Windows),`git diff` 看不到(git 自己正規化)
  但工作區真的被改寫了——症狀是 `git status` 標一排 M 而 diff 是空的
- **還原原始碼不夠,`.pyc` 也要丟**。Python 判斷 bytecode 快取只看
  (mtime, size),而突變常是等長替換、還原又在同一秒內——還原後的原始碼
  配上突變版的 bytecode 被判定為有效,症狀是**程式碼看起來完全正常、
  測試卻紅著**,怎麼讀都找不出原因
- **故障注入的突變值別踩邊界**。把保留天數改成 0 會讓 cutoff 正好等於「現在」,
  紅不紅取決於幾微秒的時間差,兩種結果都會出現,一度把真的洞誤判成有人守著
- **測試絕不碰真實資料與真實硬體**(見 `conftest_isolation.py`)

## 這個 Skill 自己的維護規則

**雙向同步**:新專案踩到的**通用**教訓要回填這裡,下一個專案自動繼承。
判準是「這條換個語言/框架還成立嗎」——成立才回填,否則留在那個專案的
`CLAUDE.md` 就好。

**尚未驗證、想試再試的**(不要當成建議照做):

- **Hooks**:把規則升級階梯的第 4 級落地(`PostToolUse` 跑測試/掃舊字串、
  `PreToolUse` 擋危險操作、`Stop` 提醒同步文件)。外界共識是「規則要被強制
  執行就用 hook,脈絡知識才用 Skill」,方向明確但來源專案還沒實測
- **`.claude/rules/*.md` + path glob**:比「觸發語指路」更確定的載入方式
- **spec-driven development**:需求明確的專案值得試「先寫規格再實作」,
  跟本 Skill 建議的「功能穩定後再補規格」方向相反,兩者適用場景不同
- **全自動 mutation 工具**(mutmut / cosmic-ray):當**探照燈**用來找盲區可以,
  但別取代手挑——手挑那套的 `why` 欄位(使用者會遇到什麼事)是自動工具給不了的
